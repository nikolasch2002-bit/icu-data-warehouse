# Transform with dbt rather than hand-rolled SQL scripts

## Context and Problem Statement

Raw tables become staging views, then a star schema, then public views: about 30 models that depend on each other, each needing tests. How should these transformations be built, ordered and tested?

## Decision Drivers

* Models must run in the right order, and adding one must not mean editing a run script.
* Every model needs tests that run on every build.
* The same code must build locally, on a CI branch and on Neon `main`.
* The transformations should stay plain SQL.

## Considered Options

* dbt-core with dbt-postgres
* Plain `.sql` scripts run in a fixed order by Python or a Makefile
* Views and stored procedures created directly in the database

## Decision Outcome

Chosen option: **dbt-core**, because it works out the build order from the models themselves, runs tests as part of the build, and builds any environment from the same code.

### Consequences

* Good, because models refer to each other with `ref()`, so dbt knows the dependency graph and builds in the right order; `dbt build -s model+` rebuilds one model and everything downstream.
* Good, because 235 checks (generic tests such as `unique` and `relationships`, plus singular SQL tests) run on every build, and a failed test stops anything downstream from being built on bad data.
* Good, because only environment variables change between local Docker, a CI branch and Neon `main`.
* Good, because hooks let security objects be attached in the same transaction that builds a table (see [ADR 0008](0008-security-objects-built-by-dbt.md)).
* Bad, because Jinja inside SQL is one more thing to learn, and sqlfluff needs stand-ins for dbt's functions and the project's macros.
* Bad, because dbt's local files (`partial_parse.msgpack`, `dbt.log`) contain the HMAC key, so `dbt/target` and `dbt/logs` must never be published beyond the generated docs.

### Confirmation

`dbt build` runs in CI on every push: 235 of 235 checks pass.

## Pros and Cons of the Options

### dbt-core

* Good, because of the dependency graph, built-in tests and lineage docs.
* Bad, because it adds a tool and a templating language.

### Ordered SQL scripts

* Good, because there is nothing new to learn.
* Bad, because the order must be maintained by hand, and tests would have to be built from scratch.

### Views and procedures in the database

* Good, because everything stays in Postgres.
* Bad, because the logic lives in the database rather than in versioned files, and there is no test framework.
